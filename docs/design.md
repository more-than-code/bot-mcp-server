# bot-mcp-server: per-repo design

**Date:** 2026-10-13. **Status:** Approved design (D1–D31), wave 1 = phase 1.
Cross-repo design: umbrella `docs/design-bot-agent-deploy.md` §7. Contracts: `docs/contracts/api-v1.md`, `docs/contracts/oauth-v1.md`.

## Layout

```
cmd/bot-mcp-server/   MCP server: Streamable HTTP at /mcp, GET /health
cmd/deploybot/        CLI: `deploybot login` (device flow), `deploybot logout`
internal/apiclient/   typed client for api-v1 (delegated bearer on /v1)
internal/tools/       one file per tool; schemas and handlers
```

## Auth

- **Host allowlist.** Before the token exchange, `/mcp` accepts a `Host` that is the `BOT_MCP_PUBLIC_ORIGIN` host, compared case-insensitively: the bare name or the scheme's default port (`443` for https, `80` for http), or exactly the port when the origin names a non-default one (an explicit default port counts as none). It also accepts `localhost`, `127.0.0.1`, and `[::1]`, with or without a port. Any other `Host`, including an empty one, is HTTP 403 `forbidden: invalid Host header`. The handler does not call the exchange, and it does not log or return the header value. The SDK's localhost protection is disabled because this list replaces it, so a proxy can pass the public `Host` through to the loopback listener. A Caddy `header_up Host` line is not needed. `/health` and `/.well-known/oauth-protected-resource` are not checked.
- Every MCP HTTP request must carry `Authorization: Bearer <token>`. Missing → HTTP 401 with `WWW-Authenticate: Bearer resource_metadata="<origin>/.well-known/oauth-protected-resource"`.
- `/.well-known/oauth-protected-resource` names the bot-api-server origin (scheme, host, port) as the authorization server and advertises `scopes_supported: ["deploybot"]`. `BOT_MCP_API_URL` must be that origin: a path other than `/`, a query, or a fragment is refused at startup. Browser clients use the authorization-code flow (`docs/spec-mcp-oauth.md`, contract `docs/contracts/oauth-v1.md`). `deploybot login` stays the headless fallback.
- **Token scope (umbrella D35, confirmed by Joe):** a token is a session of the user's account (`app.sessions`, no project column). It reaches exactly the projects the user belongs to, with the user's role in each, checked live by bot-api-server's `authz.Authorize` on every call (non-member → `not_found`, role too low → `forbidden`). This is intended; there are no per-project tokens.
- **Token exchange (umbrella D36 ended).** The server holds one client secret (`BOT_MCP_CLIENT_SECRET_FILE`, mode 0600, at least 32 characters, client id `bot-mcp-server`) and never acts without a user token. For every `/mcp` request it exchanges the caller token at the API origin (`POST /oauth/token`, `client_secret_basic`, token-exchange grant, `resource` = API origin) unless a cached delegated token exists. The cache is in memory, keyed by SHA-256 of the caller token, expires 30 seconds before `expires_in`, and drops the oldest entry past 10 000. At most 256 exchanges run at once; one more distinct caller token is HTTP 503 and is not sent to the authorization server. A subject refused with `invalid_grant` or `invalid_request` is remembered for 60 seconds (same SHA-256 key, at most 10 000, oldest dropped) and answered 401 with no further exchange. A transport error or a 5xx is not remembered. `/v1/*` is called with only the delegated token. The caller token is not sent upstream and is not passed to tool code. Exchange `invalid_grant` or `invalid_request` → HTTP 401 with `WWW-Authenticate: Bearer error="invalid_token", resource_metadata=…` before any MCP handling. An unreachable authorization server or a 5xx → HTTP 503, so the client does not discard its token. A 401 from the API during a tool call drops that cache entry and is still a tool error `unauthorized: <msg>` (HTTP 200): the MCP Go SDK v1.8.0 cannot return HTTP 401 from inside a tool result. Any other API error becomes a tool error with the API's `code` and `msg`. Neither token nor the client secret is logged.

## Catalog tools (api-v1 v1.6 programs, v1.8 images, D25)

Added 2026-10-15. Image deploy and rollback added with api-v1 v1.8. Every call still uses only the delegated token.

| Tool | Args | API |
|---|---|---|
| `list_catalog` | `project_id` | GET `/v1/projects/{id}/catalog` |
| `run_entry` | `project_id`, `entry`, `host_id`, `idempotency_key` | POST `…/catalog/{entry}/run` |
| `stop_entry` | same | POST `…/catalog/{entry}/stop` |
| `restart_entry` | same | POST `…/catalog/{entry}/restart` |
| `deploy_entry` | `project_id`, `entry`, `host_id`, `idempotency_key`, `force?` | POST `…/catalog/{entry}/deploy` |
| `rollback_entry` | `project_id`, `entry`, `host_id`, `digest`, `idempotency_key` | POST `…/catalog/{entry}/rollback` |
| `get_health_checks` | `service_id` | GET `/v1/services/{id}` |
| `set_health_checks` | `service_id`, `checks`, `idempotency_key` | PUT `/v1/services/{id}/health-checks` |
| `create_catalog_entry` | `project_id`, `name`, `spec`, `idempotency_key` | POST `/v1/projects/{id}/catalog` |
| `update_catalog_entry` | `project_id`, `name`, `spec`, `idempotency_key` | PUT `/v1/projects/{id}/catalog/{name}` |
| `delete_catalog_entry` | `project_id`, `name`, `idempotency_key` | DELETE `/v1/projects/{id}/catalog/{name}` |
| `confirm` | `confirmation_id`, `idempotency_key`, `project_id?`, `entry?` | POST `/v1/confirmations/{confirmation_id}` |
| `entry_logs` | `project_id`, `entry`, `host_id`, `lines?` | POST `…/catalog/{entry}/logs` |
| `entry_status` | `project_id`, `entry`, `host_id` | POST `…/catalog/{entry}/status` |

`list_catalog` returns only `{"items":[...]}`. A program item is `name`, `kind`, `command_display`, and `my_actions` (strings only). An image (`kind` `image`) also returns the image reference (`spec.image`, otherwise `command_display`), `image_kind` (`service` or `job`), ports (`host` and `container` only when they are numbers, `public` only when it is a boolean), volume short names, managed file names (api-v1 v1.9 `spec.files[].file`), env key names (plain and secret, sorted, no values), and env set names. `my_actions` includes `deploy` when the API grants it. Command, entrypoint, user, volume targets, file targets and contents, restart, memory, and every other catalog field are dropped. A body that is not an object with an `items` array is `error: catalog response was not usable` and is not returned. Kept strings have control characters replaced. list_catalog returns no env values. There is no container remove tool and no env-set or registry tool. `create_catalog_entry`, `update_catalog_entry`, and `delete_catalog_entry` (api-v1 v1.12) return the API plan and a confirmation id and do not change the catalog. The plan keeps inline env values and `secret_env` sources. Control characters in it are replaced. It is shown in full up to 4278613 runes. A longer plan is an error (`plan too long to show`) and returns no confirmation id. Nothing changes until `confirm`. Program entries are console-only. Secret env values belong in env sets entered in the console. `confirm` of a catalog write does not contact the host. HTTP 201 is the created entry and HTTP 200 with an entry is the replaced entry, both projected like one `list_catalog` image item. HTTP 200 with a null payload says the entry was deleted. Env values, secret_env values, and file contents are not returned. Running containers are not stopped.

`run_entry`, `stop_entry`, `restart_entry`, `deploy_entry`, `rollback_entry`, and `set_health_checks` are real and audited. They do not act. `set_health_checks` replaces every health check on a service. The caller passes `idempotency_key`, and the PUT body is `{"checks","idempotency_key"}`. `confirm` must use that same key; a different key is refused and nothing changes. `expect_status_min` and `expect_status_max`, when set, are 200–399. Nothing changes until `confirm`. Checks connect only to 127.0.0.1 on the host. Read the current checks with `get_health_checks` first. The set replaces all checks. `get_health_checks` returns `health_checks`, `name`, `ports`, and `health`, and drops every other field. A `set_health_checks` plan is shown in full up to 10886 runes. A longer plan is an error (`plan too long to show; send fewer checks`) and is not shortened. Run, stop, restart, deploy, and rollback still cap a plan at 1024 runes. `confirm` of a body with a `checks` array reports how many health checks were set and keeps only HealthCheck fields, whatever other keys the body has. The 202 result is the same plan and confirmation id as the catalog actions. Deploy and rollback require the deploy permission, and the host must run containers; the API enforces both. The API answers **202** `{"confirmation_id","plan","expires_at"}`. Any other status on those tools, including 200, is a tool error (`expected a confirmation`) and is not shown as a result. The 202 result shows the plan and the confirmation id and says nothing ran yet. The structured payload keeps only `confirmation_id`, `plan`, `expires_at`, `history`, and `force` when it is true. Run, stop, restart, deploy, and rollback redact `plan` and cap it at 1024 runes. A catalog-write plan is not redacted. An image deploy result keeps `deploy` outcome, digest, and exit code, `status`, and redacted `lines`. Other fields on those bodies are dropped. `digest` is `sha256:` plus 64 lowercase hex digits. `deploy_entry` then reads `GET …/deploys?host_id=` and attaches the newest 3 rows as `history` (`digest` full, `outcome`, `time` from `finished_at` or else `started_at`). The text shows a 12-hex digest. A failed history read still returns the plan. Rollback does not attach history. After the user agrees, `confirm` posts `{"idempotency_key"}`. Optional `project_id` and `entry` stay on the MCP call; both are required together when either is set. HTTP 200 for a program is the program status. HTTP 200 for a health-check confirm is how many checks were set; the structured body keeps HealthCheck fields and drops the rest. HTTP 200 for an image deploy is the outcome, short digest, exit code (including 0), and the last 3 log lines. The structured `lines` array still has the redacted tail. That call contacts the host. When `force` was true, the structured result has `force: true` and the plan says so. Logs and status never need confirmation. For an image, logs name the container and status reports container state, short digest, exit code, and restart count. `status.state` may be `unknown` when a deploy or rollback timed out; the text says unknown. Any other state is not shown. `entry_status`, and a confirm body that is only a status, return `error: status response was not usable` and do not return the body. On a deploy result the outcome stays and `status` is omitted. `deploy_entry` and `rollback_entry` still return only the 202 plan; the timeout status is on the `confirm` that completes them.

Inputs are refused before the API call: `entry` matches `^[a-z0-9][a-z0-9-]{0,47}$`, ids are UUIDs, `idempotency_key` is 1–128 characters from `[A-Za-z0-9._:-]`, `confirmation_id` is 43 base64url characters, `digest` matches `^sha256:[0-9a-f]{64}$`, and `lines` is 1–1000 when set (omitted lines let the API default to 200). API errors pass through as `code: msg`, and `msg` is redacted with the same line redaction. Every `lines` array (logs, and `lines` on a confirm or status payload) is redacted with the agent-protocol v1.0.3 URL pattern and then the v1.0.2 keyword pattern, each line capped at 2048 bytes, total at most 64 KiB. A `lines` value that is not an array of strings is not returned raw: a string is redacted into one line, and any other shape is dropped. A shortened line or a dropped line sets `truncated`. The same 200-item list cap still applies after that.

The confirm that runs a deploy or rollback is synchronous and can take minutes. The API client keeps a zero `http.Client.Timeout` and sets a context deadline per call. The default stays 35s. `deploy_entry` and `rollback_entry` use that default: they only reserve a confirmation. `confirm` without `project_id` and `entry`, and `confirm` of a known program, also use it. `confirm` of an image, an unknown entry, or after a failed catalog read waits at most 50s (`apiclient.MaxCallTimeout`, changed from per-entry budgets of up to 4000s on 2026-10-16, Joe). MCP clients end tool calls after about a minute, so a pull plus health wait reached the caller as a transport timeout. The API runs deploy, rollback and remove on a context without cancel, so the action finishes on the host after the 50s and `entry_status` shows the result. Only that image confirm maps a deadline to `error: still running on the host, check entry_status later`. Other deadlines and transport failures stay `error: api request failed`. The HTTP server `WriteTimeout` is 70s. Only the confirm that is about to perform an image deploy or rollback, or whose budget is unknown, extends that response's write deadline, to the budget plus 70s. A program confirm and every other request stay at 70s. `/health` does not extend. A dropped client cancels the upstream call, which does not stop an image deploy, rollback or remove on the API. There is no cap on how many long confirms run together. `ReadTimeout` and `IdleTimeout` are unchanged.

## `deploybot login`

Device flow against `--api <base-url>` (or `DEPLOYBOT_API_URL`): request a code, print the URL and user code, poll at `interval` (honour `slow_down`), and save the token to `~/.config/deploybot/token` (mode 0600, directory 0700). `--print` prints the token instead of saving it. `deploybot logout` calls `/v1/auth/signout` and deletes the file.
